# 自托管可安装 PWA 在线便笺需求提案（proposal）

## 1. 项目目标与范围

### 1.1 项目目标
构建一个**自托管、可安装（PWA）**的在线便笺应用，支持离线优先、前端加密、跨设备同步，满足日常便笺记录与检索需求。

### 1.2 本提案约束（已确认）
- 第一版不是最小闭环，需在 MVP 中优先加入：**标签、全文搜索、置顶/颜色**。
- 加密与解锁：
  - 使用**单一主密码**解锁。
  - 密钥派生算法采用 **PBKDF2**（MVP）。
  - 接受“忘记主密码即不可恢复数据”。
- 同步策略：
  - 冲突处理采用**最后写入覆盖（LWW）**。
  - 同步触发采用**手动 + 自动**并行。
- 服务端存储采用 **SQLite**。
- 本文档不要求提供完整 Docker Compose、反向代理或 HTTPS 编排细节。

## 2. 需求清单

## 2.1 功能需求（Functional Requirements）

### FR-01 便笺管理
- 支持创建、查看、编辑、删除便笺。
- 每条便笺至少包含：`id`、`title`、`content`、`createdAt`、`updatedAt`。

### FR-02 标签系统
- 支持为便笺添加多个标签。
- 支持按单标签或多标签筛选便笺。

### FR-03 视觉管理（置顶/颜色）
- 便笺支持颜色属性（预设色板）。
- 支持置顶，置顶便笺在列表/墙视图中优先显示。

### FR-04 全文搜索
- 支持对标题与正文进行全文搜索。
- 搜索结果应按相关性或更新时间排序（MVP 采用更新时间优先）。

### FR-05 离线优先
- 在无网络状态下，用户可完成创建、编辑、删除、搜索等核心操作。
- 离线变更在恢复网络后可参与同步。

### FR-06 PWA 可安装
- 提供 Web App Manifest。
- 提供 Service Worker 以支持离线缓存和应用安装体验。
- 满足桌面 Chrome “保存为应用”可安装要求。

### FR-07 加密与解锁
- 用户以主密码解锁数据。
- 使用 PBKDF2 派生密钥，数据以 AES-GCM 加密后存储。
- 服务端仅保存密文与必要元数据，不保存明文内容。

### FR-08 同步机制
- 提供手动同步入口。
- 提供自动同步机制（应用启动、网络恢复、定时触发）。
- 同一条便笺冲突时，采用最后写入覆盖（LWW）。

### FR-09 自托管后端
- 后端提供静态资源服务与同步 API。
- 使用 SQLite 存储密文数据与同步元信息。

---

## 2.2 非功能需求（Non-Functional Requirements）

### NFR-01 隐私与安全
- 明文不得在服务端落盘。
- 主密码不得明文传输或持久化。
- 密钥派生参数应可配置并具备升级空间。

### NFR-02 可用性
- 常见桌面端现代浏览器可用（优先 Chrome）。
- 在弱网和短时断网下保持可操作。

### NFR-03 性能
- 目标：常规规模（1,000 条便笺）下本地搜索与列表渲染应保持可接受交互延迟。

### NFR-04 可维护性
- 前后端模块边界清晰（加密、存储、同步分层）。
- API 版本化（如 `/api/v1`）便于后续演进。

## 3. 威胁模型与安全边界

## 3.1 保护目标
- 保护便笺明文内容、标签语义、编辑历史隐私。

## 3.2 假设与边界
- 服务端与传输链路默认不可信，服务端仅可见密文。
- 客户端运行环境（浏览器、终端设备）被攻破不在本阶段完全防护范围内。
- 用户遗忘主密码时，数据不可恢复（已接受）。

## 3.3 主要威胁
- 服务端数据库泄露导致密文外泄。
- 中间人窃听导致请求载荷泄露（应配合 HTTPS，虽非本提案交付内容）。
- 弱密码导致离线暴力破解风险。

## 3.4 缓解措施（MVP）
- PBKDF2 + 足够迭代参数提升破解成本。
- AES-GCM 提供机密性与完整性。
- 客户端最小化敏感信息缓存与日志。

## 4. 数据模型与同步协议

## 4.1 客户端便笺逻辑模型（明文态）
```text
Note {
  id: string,
  title: string,
  content: string,
  tags: string[],
  color: string,
  pinned: boolean,
  createdAt: string(ISO8601),
  updatedAt: string(ISO8601),
  deleted: boolean
}
```

## 4.2 传输/服务端模型（密文态）
```text
EncryptedNoteRecord {
  noteId: string,
  cipherText: bytes/base64,
  nonce: bytes/base64,
  aad: optional,
  updatedAt: string(ISO8601),
  deleted: boolean,
  clientId: string
}
```

> 说明：服务端不解析业务明文字段，只依赖元数据完成同步裁决。

## 4.3 同步协议（MVP）
- 客户端维护本地变更队列（增删改）。
- 手动触发或自动触发时，提交增量变更。
- 服务端按 `noteId` 对比 `updatedAt` 执行 LWW。
- 服务端返回自上次同步点以来的远端增量。
- 客户端应用远端增量并更新本地状态。

## 4.4 冲突处理规则（LWW）
- 若本地与远端同一 `noteId` 均有改动，比较 `updatedAt`。
- 时间较新的版本覆盖较旧版本。
- 时间戳一致时，以 `clientId` 字典序作为确定性兜底。

## 5. API 草案（/api/v1）

## 5.1 认证/会话（MVP 简化）
- MVP 可先采用设备级 API Token（部署端配置），后续再扩展多用户认证。

## 5.2 同步接口
### `POST /api/v1/sync/push`
- 入参：客户端增量变更数组（密文记录）。
- 出参：接收结果（成功/失败条目、服务器时间戳）。

### `GET /api/v1/sync/pull?since=<cursor>`
- 入参：上次同步游标。
- 出参：增量密文记录列表 + 新游标。

### `POST /api/v1/sync/full`
- 用途：新设备首次全量拉取（密文）。

## 5.3 健康检查
### `GET /healthz`
- 出参：服务状态、版本号、数据库连通性摘要。

## 6. 里程碑计划（MVP → v1.0）

## M1：基础可用（本地离线）
- 便笺 CRUD
- 标签、置顶/颜色
- 本地全文搜索
- IndexedDB 存储

## M2：加密闭环
- 主密码解锁流程
- PBKDF2 派生密钥
- AES-GCM 本地加密存储

## M3：同步闭环
- `/sync/push` 与 `/sync/pull`
- SQLite 密文存储
- 手动 + 自动同步
- LWW 冲突策略

## M4：PWA 安装与稳定性
- Manifest + Service Worker
- 离线缓存策略完善
- 基础错误处理与重试

## M5：v1.0 打磨
- 交互优化、性能优化
- 安全参数与配置化
- 文档完善与部署说明

## 7. 验收标准（可测试条目）

### AC-01 功能验收
- 能创建、编辑、删除、检索便笺。
- 标签筛选可正确返回对应便笺。
- 置顶与颜色设置可持久化。

### AC-02 离线验收
- 断网后可继续新增/编辑/删除与搜索。
- 恢复网络后可成功同步离线期间变更。

### AC-03 安全验收
- 服务端数据库中不可见便笺明文。
- 更换错误主密码无法解密已有数据。

### AC-04 同步验收
- 两设备修改同一便笺时，最终状态符合 LWW。
- 手动同步与自动同步均可触发并成功执行。

### AC-05 PWA 验收
- 浏览器可安装应用。
- 二次打开应用可离线启动基础功能。

## 8. 风险与取舍

## 8.1 已接受取舍
- 忘记主密码不可恢复：换取更强的零信任隐私边界。
- LWW 冲突简单易实现：可能覆盖用户较早但重要的修改。

## 8.2 主要风险
- PBKDF2 参数设置不当导致抗暴力破解能力不足。
- 客户端时间漂移影响 LWW 判定准确性。
- Service Worker 缓存更新策略不当导致“旧资源滞留”。

## 8.3 后续优化方向
- 增加冲突副本模式（可配置）。
- 引入更强 KDF（Argon2id）与参数升级机制。
- 引入更细粒度同步游标与幂等机制。
